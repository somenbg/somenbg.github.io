01

Distributed GPU machine learning platform

Ray and KubeRay on Amazon EKS for distributed training, data processing, and GPU batch inference.

Distributed systemsMLOpsGPU infrastructure

Implemented · evolving

Problem

Training and inference had to move off single-machine workflows onto shared Kubernetes infrastructure, with heterogeneous GPUs, large datasets, and a real cost constraint.

Engineering decisions

  • KubeRay owns Ray cluster lifecycle on EKS, instead of hand-managed processes.
  • Ray Train and TorchTrainer run PyTorch Distributed Data Parallel across GPU workers.
  • Ray Data, PyArrow, and S3 handle distributed processing and feature paths feeding those jobs.
  • GPU memory, batch shape, and parallelism are measured before instance families are chosen.

Challenges

  • Allocating GPUs without stranding memory or leaving accelerators idle.
  • Training across nodes without making the data path the bottleneck.
  • Keeping concurrency high while inference cost stays below the CPU alternative.

Results

  • Distributed GPU training running on Ray and PyTorch.
  • GPU batch inference approximately 2–3× faster than CPU execution.
  • Inference compute cost approximately one-half to one-third of the CPU baseline.

Takeaway

The speedup showed up after batching, placement, and data movement were treated as part of the job, not after the cluster was simply made larger.

02

Agentic AI engineering assistant

An internal assistant that pairs LLM reasoning with infrastructure and enterprise data tools.

Agentic AILLM applicationsDeveloper tools

Working proof of concept

Problem

Engineers needed a way to retrieve operational information and inspect internal technical resources without turning every question into a manual hunt across systems.

Engineering focus

  • Tool orchestration with explicit access boundaries.
  • Stateful conversations persisted in DynamoDB.
  • Retrieval-augmented answers over internal knowledge.
  • Credential handling through AWS Secrets Manager, not embedded secrets.
  • Reliability and observability of the agent loop.

Takeaway

The useful version of this system is defined by which tools it is allowed to call, and how that access is scoped, as much as by the model behind it.

04

AI-driven automated research framework

An experiment in letting an LLM propose training modifications, then judging them against a fixed baseline.

AI researchAutomated experimentation

Experimental proof of concept

Approach

  1. Establish a reproducible baseline.
  2. Ask an LLM for candidate modifications.
  3. Execute the experiments.
  4. Score them against defined metrics.
  5. Keep promising configurations.
  6. Iterate on the next hypothesis.

First evaluation domain

The Kaggle Porto Seguro Safe Driver Prediction dataset. The questions under test are whether an LLM can propose useful experiments, how results should be compared, how to cap compute, how to sandbox execution, and what safeguards AI-generated code needs.

Scope

Experimental research. No production performance improvement is claimed.

06 — Philosophy

Scalable, measurable, secure, and maintainable.

Performance through measurement

Benchmark, profile, and experiment before an architecture choice hardens. The number decides, not the diagram.

Infrastructure as a product

ML infrastructure should remove repeated platform work for engineers and data scientists, not recreate it per project.

Security by design

Access control, workload isolation, and operational visibility belong in the architecture, not in a later review.

Cost-aware scalability

Optimize for performance per dollar. Maximum capacity is not the same thing as a good system.

Reproducible machine learning

Workflows need consistent execution, versioning, traceability, and experiments that can be run again.

Continuous learning

New tools in distributed ML, GPUs, agents, and cloud-native infrastructure get evaluated for engineering value, then adopted or left alone.
